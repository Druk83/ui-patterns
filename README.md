# ui-patterns

Публичный co-repository проверенных UI-паттернов для подготовки технической UI-документации.

Репозиторий не содержит требований конкретного продукта. Он задаёт правила выбора паттерна, обязательный контекст решения и структуру результата.

Версия набора шаблонов: `0.3.2`

Релиз `0.3.2` опубликован 2026-10-22.

## Точка входа агента

1. Прочитать `ui-pattern-selection.md`.
2. Загрузить `pattern-catalog.yml`.
3. Извлечь из требований проекта обязательный контекст экрана.
4. Сопоставить контекст с условиями и противопоказаниями паттернов.
5. Зафиксировать выбранный паттерн, отклонённые альтернативы и `GAP`.
6. Применить `ui-pattern-application-templates.yml`.
7. Применить подходящие сквозные шаблоны, включая `information-architecture-ui` при необходимости, и зафиксировать решения по UX-принципам и структуре содержимого.
   Для подтверждённого многораздельного лендинга проверить
   `landing-page-composition-ui`; его эталон `landing-page-screen` хранит
   ссылки на базовые паттерны по блокам.
8. Сформировать или актуализировать пул экранов (screen pool) по
   `шаблоны-экранов/контракт-пула-экранов.yml`. Это рекомендуемый порядок, а не
   запрет начинать UI-проектирование раньше: по запросу разработчика агент может
   начать с экранов, шаблонов и viewport-кандидатов, помечая результат как
   `draft`/`proposed` до подтверждения пула.
9. Для визуального экрана выбрать шаблон композиции из
   `шаблоны-экранов/manifest.json`. Эти шаблоны описывают содержимое, зоны и
   состояния, но не являются точными оболочками устройств или viewport.
10. Для каждого выбранного сочетания «экран × viewport × ориентация» найти
    оболочку в каталоге, предоставленном проектом-потребителем, и проверить точное
    совпадение размеров и ориентации. Контракт интеграции: `screen-shell-integration-contract.md`.
    Если совпадения нет, записать `GAP`; не заменять оболочку приблизительным
    адаптивным макетом. `not_applicable` использовать только для невизуального
    артефакта; экранный VUI/NUI также привязывается к оболочке.
11. Формировать финальную UI-спецификацию по `ui-screen-specification-template.md`
    и проверять результат по `ui-specification-schema.yml`; финальный статус
    присваивать после подтверждения пула и решений по оболочкам.

## Режимы работы

При использовании каталога агент читает только публичный слой. До выбора ему нужны `ui-pattern-selection.md` и `pattern-catalog.yml`; карточка семейства по `card_path` и шаблон по `template_id` из `ui-pattern-application-templates.yml` загружаются только для выбранных кандидатов. Внутренний слой разработки не является обязательным входом для выбора паттерна.

При разработке или обновлении самого каталога агент дополнительно читает внутренние реестры, манифесты и задачи. Они содержат источники, доказательства, контракты, правила версий и отчёты проверки и не входят в публичный пакет.

Внутреннее руководство PlantUML используется только при разработке и проверке диаграмм каталога. Оно не является обязательным входом для выбора паттерна и не задаёт визуальный стиль проекта, использующего каталог.

## Публичные артефакты

- `pattern-catalog.yml` — decision catalog: порядок выбора, критерии, ограничения и результат.
- `ui-pattern-selection.md` — процедура обработки для агента.
- `ui-pattern-application-templates.yml` — обязательные блоки, действия, состояния, переходы, общие UX-профили и сквозные шаблоны, включая структуру содержимого, навигацию, модальность и технический контекст интерфейса.
- `ui-screen-specification-template.md` — шаблон результата по конкретному экрану.
- `ui-specification-schema.yml` — машинно-читаемый контракт UI-пакета.
- `screen-shell-integration-contract.md` — контракт связывания шаблонов содержимого
  с точными оболочками viewport, предоставляемыми проектом-потребителем.
- `pattern-catalog-check.py` — проверка связей паттернов, шаблонов, артефактов и согласованности публичных версий.
- `шаблоны-экранов/контракт-пула-экранов.yml` — контракт screen pool с типами экранов,
  кандидатами паттернов, viewport и статусами подтверждения.
- `шаблоны-экранов/` — переиспользуемые шаблоны композиции содержимого и живые
  эталонные примеры; точные оболочки устройств в каталог не входят.
- `шаблоны-экранов/лендинг/index.html` — эталон состава блоков лендинга с
  вариантами с формой и без неё; все тексты в нём являются тестовыми данными.
- В семействе `списки/` карточная лента и табличное представление являются разными паттернами с отдельными ID и эталонами; выбор зависит от формы представления данных, а не от общего факта наличия коллекции.
- `reference-prototype-check.py` — локальная runtime и visual проверка прототипов
  на подтверждённых viewport; screenshots создаются как временный результат проверки.
  Для проверки всех зарегистрированных семейств используется явный параметр
  `--all-templates --viewport WIDTHxHEIGHT`; размеры не задаются автоматически.
- `tests/test_landing_viewport.py` — точная проверка эталона лендинга через
  инструменты разработчика браузера (DevTools) на широком и узком тестовых viewport, включая вариант с формой,
  переполнение и состояния действия. Запуск: `python -B -m unittest discover -s tests -p test_landing_viewport.py -v`.
- `tests/test_landing_framework_integration.py` — изолированный путь через
  `ui-screen-scaffold` и `ui-reference validate`; для запуска задать
  `SDD_FRAMEWORK_ROOT` с установленным или исходным каталогом Framework и
  `UI_PATTERNS_REVISION` с полным SHA закреплённого коммита `ui-patterns`.
- `формы/`, `списки/`, `панели-мониторинга/`, `мобильные/`, `навигация/`, `диалоги/` — карточки и визуальные материалы паттернов; путь к карточке задаётся в `card_path`.
- `extended_templates` в `pattern-catalog.yml` и каталоги `командная-строка/`, `разговорные-интерфейсы/`, `голосовые-интерфейсы/`, `текстовые-интерфейсы/`, `естественное-взаимодействие/`, `процессы/` — активные расширенные шаблоны для выбора по обязательному контексту.

## Принципы качества

- В публичные файлы попадают только нормализованные общие правила.
- Факты конкретного проекта, приватные пути и внутренние реестры не публикуются.
- Неподтверждённое решение обозначается как `GAP`.
- Размеры viewport не выводятся из названия устройства: для каждого кандидата нужны
  CSS px, источник, обоснование, responsive-условия и статус.
- Подтверждённый screen pool является обязательным входом для финальной детализации экранов.
- Проектирование UI может начаться до подтверждения screen pool по прямому запросу
  разработчика; такой результат остаётся черновым и не выдаётся за согласованный.
- На один выбранный экран, viewport и ориентацию создаётся отдельный визуальный
  артефакт; не генерируются все возможные комбинации автоматически.
- Шаблоны каталога задают содержимое и responsive-поведение, а не внешнюю оболочку
  конкретного устройства.
- Паттерн выбирается по условиям применения и противопоказаниям, а не по визуальному сходству.
- Для карточной ленты используется отдельный шаблон; табличный шаблон предназначен для данных с повторяющейся структурой строк и колонок.
- Паттерн не подменяет требования проекта: он задаёт проверяемые ограничения и обязательные решения для UI-блоков.
