# Контракт интеграции оболочек экранов

## Назначение

Этот контракт отделяет шаблон композиции содержимого от оболочки области
отображения (viewport shell) и определяет, как проект связывает их в проверяемый
живой макет. Каталог `ui-patterns` задаёт паттерны и внутреннюю композицию UI; он
не публикует точные оболочки устройств и не назначает проекту размеры экранов.

## Термины и границы ответственности

- **Шаблон композиции содержимого (content-composition template)** — структура
  экранных зон, слотов, блоков, действий и состояний из `шаблоны-экранов/`.
- **Оболочка области отображения (viewport shell)** — готовая внешняя основа для
  конкретных ширины, высоты и ориентации: размеры рабочей области, ограничения
  безопасных областей и предусмотренные каталогом системные области. Состав
  оболочки определяется её собственным каталогом.
- **Проектный живой макет** — отдельный запускаемый артефакт, в котором содержимое
  экрана собрано внутри выбранной оболочки и связано с проектными требованиями.

Распределение ответственности:

| Источник | Ответственность |
|---|---|
| `ui-patterns` | Выбор паттерна, шаблон содержимого, слоты, состояния и поведение композиции. |
| Каталог оболочек проекта-потребителя | Готовые оболочки с идентификаторами, точными CSS px, ориентацией и правилами их применения. |
| Проект-потребитель | Пул экранов, выбранные сочетания viewport/ориентации, проектное содержимое и живые макеты. |

`viewport_contract` в манифесте `ui-patterns` описывает требования к размерам и
адаптивному поведению содержимого. Он не является готовой оболочкой. Наличие
слова `shell` в существующем идентификаторе шаблона также не означает, что этот
шаблон содержит точную оболочку устройства.

## Порядок связывания

1. Зафиксировать экран, задачу пользователя, выбранный паттерн и шаблон
   композиции. Разработчик может начать с UI до завершения остальных документов;
   до подтверждения пула экранов такие результаты имеют статус `draft` или
   `proposed`.
2. Для каждого нужного сочетания экрана, viewport и ориентации указать ширину и
   высоту в CSS px, источник, обоснование и responsive-условия. Не выводить
   размеры из названия устройства.
3. Найти оболочку в каталоге, предоставленном проектом-потребителем. Сверить
   идентификатор оболочки, точную ширину, высоту, ориентацию, безопасные области и
   поддерживаемые состояния с подтверждённым viewport-кандидатом.
   Если совпадают несколько вариантов, перечислить их как `proposed` и передать
   выбор разработчику; агент не выбирает равнозначные варианты произвольно.
4. Зафиксировать источник каталога оболочек, его неизменяемую ревизию, ID
   оболочки и ID viewport. Для статуса `selected` ссылка и все ID должны
   разрешаться в указанной ревизии.
5. Поместить содержимое шаблона в предусмотренные слоты оболочки. Не перестраивать
   её внешнюю геометрию и системные области вручную.
6. Создать отдельный живой макет для каждого сочетания экрана, выбранного
   viewport и ориентации. Не генерировать автоматически все возможные размеры и
   повороты; в результат входят только выбранные разработчиком варианты.
7. После подтверждения пула экранов согласовать черновые макеты с ним и обновить
   их статус и ссылки. Неподтверждённый макет нельзя выдавать за финальный.

## Структура артефактов проекта-потребителя

Проект-потребитель выбирает корневую папку и правила именования по своим
манифестам. Логически для каждого экрана рекомендуется хранить:

```text
<ui-root>/
└── <screen-id>/
    ├── <screen-specification>.md
    └── макеты/
        └── <shell-id>/
            ├── <width>x<height>px/
            │   ├── index.html
            │   ├── styles.css
            │   ├── script.js
            │   └── manifest.json
            └── <другой выбранный размер>px/
                └── ...
```

Каждый каталог размера содержит один самостоятельный запускаемый макет и
манифест с `screen_id`, `shell_id`, точными размерами, ориентацией, состоянием,
ссылками на требования и ревизией каталога оболочек. Поворот экрана представлен
отдельным viewport с переставленными шириной и высотой, а не только CSS
перестроением внутри одного холста. Имена каталогов могут следовать соглашению
потребителя; пример задаёт логическую структуру, а не обязательные имена.

## Состояния привязки

Каждый viewport в новом screen pool содержит непустой `screen_shell_candidates`.
Для визуального интерфейса список содержит точные варианты, `GAP` или оба типа;
для чисто невизуального результата — `not_applicable`. Если вариантов несколько,
они перечисляются отдельно, а до решения разработчика имеют статус `proposed`.
Для каждого кандидата проверяется совпадение `shell_viewport` с viewport-пулом.

В `reference_artifact.shell_binding.status` используются:

- `selected` — точная оболочка найдена, проверена и связана с артефактом;
- `proposed` — оболочка предложена, но ещё не подтверждена разработчиком;
- `gap` — подходящей оболочки нет или её параметры неизвестны; указываются
  причина и требуемое решение;
- `not_applicable` — артефакт не является визуальным экраном, например команда
  CLI/TUI; требуется краткое обоснование. VUI/NUI с визуальным экраном также
  связывается с оболочкой.

## Если оболочки нет

Агент не подменяет отсутствующую оболочку произвольной responsive-страницей,
макетом с приблизительным размером или прототипом другого устройства. Он:

1. сохраняет выбранный экран, паттерн, шаблон композиции и подтверждённые сведения;
2. регистрирует `GAP` с недостающими параметрами и решением, которое требуется
   от разработчика;
3. может подготовить черновую композицию содержимого без утверждения, что она
   воспроизводит точный экран или устройство;
4. предлагает проверить доступный каталог либо отдельно поручить создание
   проектной оболочки в репозитории-потребителе.

Проектная оболочка не добавляется в `ui-patterns`, если она отражает требования
конкретного продукта. Дополнение универсального каталога оболочек является
отдельным решением владельца этого каталога.

## Формат ссылки на оболочку

Для выбранной привязки запись в пуле и UI-пакете содержит как минимум:

```yaml
shell_binding:
  status: selected
  catalog_url: <официальный URL каталога оболочек>
  catalog_revision: <неизменяемый Git commit или tag>
  shell_id: <ID оболочки>
  viewport_id: <ID viewport из пула экранов>
  shell_viewport:
    width: <ширина в CSS px>
    height: <высота в CSS px>
    unit: css-px
    orientation: <portrait|landscape>
```

`shell_viewport` копируется из записи оболочки закреплённой ревизии и автоматически
сверяется с размерами и ориентацией родительского viewport. Локальный путь
checkout не заменяет `catalog_url` и не является источником происхождения.

## Постоянная граница ответственности каталога

Этот контракт описывает общие правила интеграции и не привязан к номеру релиза
или конкретному репозиторию-потребителю. `ui-patterns` предоставляет паттерны,
композиции содержимого и формат ссылок на оболочки, но не поставляет сами
оболочки устройств, не выбирает модели и не назначает размеры viewport.

Потребитель самостоятельно предоставляет каталог оболочек и фиксирует его
официальный URL и неизменяемую ревизию. Наличие конкретной оболочки проверяется
по фактически указанной ревизии этого каталога; ссылка в UI-пакете сама по себе
не означает, что оболочка существует.

Изменения состава конкретного релиза `ui-patterns` описываются в `CHANGELOG.md`.
Этот документ сохраняет общий контракт между версиями и репозиториями.
