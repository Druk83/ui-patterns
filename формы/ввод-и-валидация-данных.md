# Ввод и валидация данных формы

Status: active  
Version: 1.0  
Pattern ID: `ui-patterns.forms.form-data-entry-validation`  
Family: `forms`  
Pattern type: `FORM_WORKFLOW_UI`  
Decision scope: `screen-block`

## Определение

Форма ввода данных (data-entry form) объединяет поля, правила проверки и отправку введённых данных. Карточка нормализует общие свойства Ant Design Form и Form Page без переноса компонентного кода или проектных сущностей.

## Намерение

Собрать пользовательские данные, показать правила проверки и передать результат операции после успешной валидации.

## Контекст и сигналы выбора

Паттерн применим, если пользователь вводит несколько значений, для них существуют правила проверки или требуется явная отправка результата.

Сигналы выбора:

- несколько полей ввода;
- обязательные и необязательные значения;
- валидация поля или всей формы;
- отдельное действие отправки.

## Условия выбора и противопоказания

Выбирать паттерн следует при наличии пользовательского ввода и операции проверки или отправки данных. Паттерн противопоказан, если ввода нет или требуется только подтверждение уже сформированного действия.

## Границы решения

Паттерн описывает структуру ввода и проверки. Он не определяет бизнес-правила, роли, конкретные данные, текст сообщений или API-контракт проекта.

## Структура

- контейнер формы;
- поля и labels;
- подсказки и сообщения валидации;
- действие отправки;
- результат успешной или неуспешной проверки.

## Состояния и переходы

Подтверждённые источниками состояния:

- `enabled`;
- `disabled`;
- `validation-error`;
- `validation-status`.

Нормализованные переходы:

```text
edit → validation
validation-error → edit
validation-success → submit
submit → result
```

Состояния `loading`, `network-error` и `unsaved-changes` требуют решения целевого проекта и не считаются автоматически заданными этой карточкой.

## Последствия и ограничения

Положительные последствия:

- единая область ввода и проверки;
- явное связывание поля с его сообщением;
- возможность разделять форму по смысловым группам.

Ограничения:

- обязательность полей и момент валидации должны быть определены отдельно;
- сложный процесс может потребовать декомпозиции на несколько частей;
- компонентный API источника не является универсальным API проекта.

## Accessibility и responsive

Полный accessibility-контракт отсутствует в использованных источниках и должен быть получен из требований целевого проекта. Правила клавиатуры, фокуса, экранного диктора и контраста являются `GAP`, пока не подтверждены проектными источниками.

Источник допускает перенос длинных labels. Остальные правила `viewport` и `breakpoint` являются проектными ограничениями.

## Совместимость

Совместим с `ui-patterns.dialogs.modal-dialog`, если форма действительно является коротким контекстным взаимодействием. Использование формы внутри модального диалога требует отдельной проверки размера, закрытия и сохранения данных.

- Проверить состояния `enabled`, `disabled`, `validation-error` и `validation-status`.
- Проверить, что проектные правила accessibility и responsive не подменены этой карточкой.
