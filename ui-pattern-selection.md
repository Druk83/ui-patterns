# Процедура выбора UI-паттерна

Этот документ задаёт публичный порядок работы агента. Машиночитаемый каталог решений (decision catalog) `pattern-catalog.yml` является единственным источником критериев выбора и порядка проверки.

## Контур работы

1. Прочитать этот документ и `pattern-catalog.yml`.
2. Проверить обязательный контекст из `required_context`. Недостающие сведения зафиксировать как `GAP`.
3. Выполнить `selection_order` каталога: определить область UI, контекст экрана, задачу пользователя, форму данных, модель взаимодействия и ограничения.
4. Сопоставить кандидатов с `required_conditions` и `selection_signals`.
5. Исключить кандидатов по `contraindications`, проверить `compatible_with` и сохранить отклонённые альтернативы.
6. Выбрать паттерн для каждого UI-блока и зафиксировать `selected_pattern`, `applied_template` и `unresolved_gaps`.

## Отложенная загрузка артефактов

Агент не читает все карточки и шаблоны до выбора. Для выбранного кандидата он загружает:

- `card_path` — карточку паттерна из русскоязычного каталога семейства (`формы/`, `списки/`, `панели-мониторинга/` и других);
- `template_id` — запись шаблона применения (application template) в общем `ui-pattern-application-templates.yml` со связанными обязательными блоками, состояниями, действиями, переходами и проверками.

## Формирование результата

1. Заполнить `ui-screen-specification-template.md` для экрана и его UI-блоков.
2. Проверить результат по `ui-specification-schema.yml`.
3. Включить в результат данные, действия, состояния, переходы, валидацию (validation), доступность (accessibility) и адаптивное поведение (responsive behavior) только в объёме подтверждённых требований.
4. Все проектные решения, которых нет во входных данных, оформить как `GAP` с владельцем и условием закрытия.

## Ограничения

- Не выбирать паттерн по визуальному сходству.
- Не переносить в проект универсальные или иллюстративные сущности из карточки.
- Не заменять отсутствие подходящего паттерна вымышленным решением.
- Один экран может сочетать несколько паттернов, если границы их UI-блоков зафиксированы.

Результат считается готовым, если решение объяснено входным контекстом, альтернативы отклонены с причинами, обязательные проверки шаблона выполнены, а все `GAP` зарегистрированы.
